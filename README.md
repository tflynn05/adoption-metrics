# adoption-metrics: instrumenting a platform rollout

A rollout is funded to produce a business result. Adoption is the leading indicator, and it is measurable weeks before the result is. This project shows how I define "adopted," instrument it, and read the numbers to find the group that needs intervention, by week four, before the program average hides it.

It is the companion to [change-management-skill](https://github.com/tflynn05/change-management-skill): that skill produces the adoption metrics section of a change plan; this project is what happens to those metrics after go-live.

Built by [Tim Flynn](https://www.linkedin.com/in/tim-flynn), Prosci® Certified Change Practitioner.

## What is here

| Piece | What it does |
|---|---|
| [`docs/metric-definitions.md`](docs/metric-definitions.md) | The metrics I hold a rollout to: the headline three, the supporting six, the definition of "adopted," and the decision each metric exists to trigger. This is the substance; the code is the demonstration. |
| [`scripts/generate_rollout_data.py`](scripts/generate_rollout_data.py) | Simulates a 90-day rollout across five impacted groups. One group stalls in a specific way: its people log in, keep doing the real work on the legacy path, override the model, and their managers do not coach. |
| [`scripts/analyze_adoption.py`](scripts/analyze_adoption.py) | Computes the metrics per group per week and applies the reading rules to raise flags: `STALL`, `BEHIND`, `SPIKE`, `ABILITY`, `OVERRIDE`, `COACHING`. Prints a sponsor readout. |
| [`scripts/build_dashboard.py`](scripts/build_dashboard.py) | Renders a self-contained HTML readout: four small-multiple charts, the flags, and a table view. No external libraries. |
| [`dashboard.html`](dashboard.html) | The week-4 readout from the default run. |

## Run it

```
pip install pandas numpy
python3 scripts/generate_rollout_data.py            # writes data/*.csv (stalled group: channel_managers)
python3 scripts/analyze_adoption.py --as-of-week 4  # readout and flags at week 4
python3 scripts/build_dashboard.py                  # dashboard.html
```

Change which group stalls with `--stall analysts` (or `--stall none`), and the week of the readout with `--as-of-week`.

## What the week-4 readout says

Every group is at or above its active-user ramp target. On active users alone, the rollout looks fine. The flags say otherwise:

```
[channel_managers]
  STALL     active 88% but work migrated 14% vs target 25%; people are in the tool,
            not doing the real work there. Desire barrier: check legacy path and override rate
  OVERRIDE  override rate 46% above guardrail 25%; manager conversation on override discipline
  COACHING  only 14% of managers coached this week; sponsor's ask goes to the managers' leader

HEADLINE: intervene on channel_managers this week. Look at that group's sponsor before looking at that group.
```

That is the pattern I watched happen on a real enterprise AI decisioning rollout: the login numbers were green while the work stayed on the old path, and the group's managers were not having the conversation. Active users is the metric everyone reports because it is easy. Work migrated and override rate are the ones that tell you whether the change is happening.

## Design decisions

- **Adoption is declared per group and per unit, never for the program.** The program average is what hides the stalling group.
- **Every metric has a decision attached.** A metric that does not change what someone does next week is reporting, not management. The flag logic in `analyze_adoption.py` is the decision table from `docs/metric-definitions.md`, written down.
- **Targets are set before go-live and owned by the group's leader.** The ramp curve in the code is a default; on a real rollout the numbers come from the leader who will be held to them.
- **The sponsor reads one line.** The readout opens with a headline and the flags; the charts and the table are there for the people who need to argue with it.
- **Look at the sponsor before the group.** When one group is behind on everything, the cause is usually above it.

## Scope

All data is synthetic, generated by the script from the distributions it documents. The flag thresholds (ramp curve, migration targets, 25% override guardrail, 70% retention floor, 60% self-service floor) are defaults I would use as a starting point on a marketing or decisioning platform rollout; they are not universal.
